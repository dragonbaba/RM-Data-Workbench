## 1. 需求

### 背景
当前效果模式虽然已经切到 `module + config` 结构，但面板顶部仍保留“当前条目脚本模块”展示区，信息重复且没有实际编辑价值。同时 `config` 默认是空对象，用户看不到必要结构，也缺少保存前的字段级校验。

### 目标
- 移除效果模式顶部无意义的脚本模块展示区
- 新增效果项时，`config` 默认直接展示必要模板字段 `selector` 和 `args`
- 每次保存效果时，强制校验 `config.selector` 与 `config.args` 必须存在且都为对象

### 约束条件
```yaml
兼容性约束: 不做兼容层；直接按当前 config 结构收口
业务约束: 本轮只校验 selector 与 args 的存在和对象类型，不延伸到更细的业务字段
交互约束: 校验失败时阻止保存，并明确提示出错的效果序号
```

### 验收标准
- [ ] 效果模式顶部不再显示“当前条目脚本模块”卡片
- [ ] 新增效果项时，`config` 编辑框默认显示包含 `selector` 与 `args` 的 JSON 模板
- [ ] 已有不完整效果数据在归一化后也会补齐 `selector` 与 `args`
- [ ] 保存时若 `selector` 或 `args` 缺失，或不是对象，则阻止保存并给出提示

---

## 2. 方案

### 技术方案
在 `GameEffectService` 中抽出统一的默认 `config` 模板与校验逻辑，让面板初始化、新增效果和保存前验证都走同一套规则。`EffectPanel` 仅负责移除冗余展示区、复用默认模板生成 JSON 文本，并在提交前调用服务层校验结果后再保存。

### 影响范围
```yaml
涉及模块:
  - 前后端交互与性能修复记录: 效果模式面板交互与错误提示
  - 数据加载与地图管理: gameEffects.config 默认模板与校验收口
预计变更文件: 3
```

### 风险评估
| 风险 | 等级 | 应对 |
|------|------|------|
| 旧数据缺少必要字段导致用户首次保存失败 | 中 | 归一化时自动补齐默认模板，降低首次进入后的手工修复成本 |
| 面板文案调整后用户找不到模块来源 | 低 | 保留每个效果项内的 `脚本模块` 下拉，删除的只是顶部重复信息区 |

## 4. 核心场景

### 场景: 新增效果默认模板
**模块**: 前后端交互与性能修复记录
**条件**: 用户在效果模式点击“添加效果”
**行为**: 编辑器创建带有 `selector` 和 `args` 的默认 `config`
**结果**: 用户可以直接在模板基础上填写配置，而不是从空对象开始

### 场景: 保存前必要字段校验
**模块**: 数据加载与地图管理
**条件**: 用户点击“保存效果”
**行为**: 逐条解析 JSON，并校验 `selector`、`args` 都存在且为对象
**结果**: 不合规数据被拦截，不会写回到当前数据文件

## 5. 技术决策

### effect-config-template-validation#D001: config 默认模板与校验逻辑下沉到服务层
**日期**: 2026-03-21
**状态**: ✅采纳
**背景**: 面板初始化、新增效果和保存校验都需要使用同一套必要字段规则，如果只在组件里散落处理，后续字段扩展时容易分叉。
**选项分析**:
| 选项 | 优点 | 缺点 |
|------|------|------|
| A: 仅在 `EffectPanel` 内联默认模板和校验 | 改动表面更少 | 规则分散，测试覆盖弱 |
| B: 在 `GameEffectService` 提供默认模板和校验函数 | 规则集中，便于测试与复用 | 需要同步调整服务层测试 |
**决策**: 选择方案B
**理由**: 这是数据结构层规则，不应只停留在 UI 组件里。
